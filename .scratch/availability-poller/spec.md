# Spec: 예약 가능 자리 폴러 (1차: 영덕 고래불 국민야영장)

Status: ready-for-agent

출처: [map.md](map.md)(결정 인덱스), `issues/*.md`(결정별 세부 내용), `research/*.md`(조사 근거). 용어는 저장소 루트의 `CONTEXT.md`를 따른다. **예약처 / 시설 / 구역 / 자리 / 감시 조건 / 조회 단위 / 바퀴 / 빈자리**.

## Problem Statement

인기 있는 공공 캠핑장은 원하는 날짜와 자리가 거의 늘 매진이다. 취소나 미결제 자동취소로 자리가 풀리는 때가 있지만 언제 풀릴지 알 수 없다. 누군가 먼저 잡아 가기 전의 짧은 시간 안에 그 자리를 발견해야 한다. 지금은 사람이 예약 페이지를 수시로 새로고침하는 방법밖에 없다. 고래불 국민야영장은 날짜를 30일 롤링으로 열고, 선착순으로 받으며, 최대 2박까지 예약할 수 있다. 2박 예약이 취소되면 자리는 0~3시간 사이 임의 시각에 다시 풀린다. 그래서 사람이 지켜보기가 특히 어렵다.

## Solution

사용자는 설정 파일에 감시 조건을 적는다. 감시 조건은 "어느 시설의, 어느 구역과 자리가, 어느 입실일 범위와 요일에, 최소 몇 박 연속으로 비면"이라는 형식이다. 상주하는 폴러가 예약처를 사람이 쓰는 속도에 가깝게 조회한다. 기본 간격은 예약처당 150초다. 감시 조건에 맞는 빈자리가 새로 생기면 Telegram으로 알림을 보낸다. 알림에는 시설, 구역, 자리 번호, 숙박 구간, 해당 감시 조건이 들어가고, 예약 화면으로 바로 가는 링크 버튼이 붙는다. 폴러가 차단당하거나 사이트 구조가 바뀌어 감시를 할 수 없게 되면 그 사실도 알린다. 사용자는 알림이 오지 않는 이유를 "빈자리가 없어서"로 오해하지 않게 된다.

폴러는 예약처의 방어 장치(대기열, captcha, 봇 탐지)를 우회하지 않는다. 브라우저로 위장하지 않고 도구 이름을 밝힌 User-Agent를 쓴다. 차단 신호를 받으면 멈춘다. 자동 예약은 하지 않는다.

## User Stories

### 감시 조건 설정

1. 캠핑 이용자로서, 시설과 구역을 지정한 감시 조건을 설정 파일에 적고 싶다. 원하는 구역만 감시하기 위해서다.
2. 캠핑 이용자로서, 구역 안의 특정 자리 번호(`A02`)나 범위(`A10-A15`)만 감시하고 싶다. 선호하는 자리만 알림받기 위해서다.
3. 캠핑 이용자로서, 자리 번호를 생략하면 구역 안의 모든 자리가 감시되기를 원한다. 설정을 짧게 쓰기 위해서다.
4. 캠핑 이용자로서, 입실일 범위(`from`~`to`)를 지정하고 싶다. 가능한 날짜 안에서만 알림받기 위해서다.
5. 캠핑 이용자로서, 입실 요일(예: 금, 토)로 거르고 싶다. 주말 캠핑만 노리기 위해서다.
6. 캠핑 이용자로서, 최소 연박 수(N)를 지정하고 싶다. 2박이 연속으로 비는 자리만 알림받기 위해서다.
7. 캠핑 이용자로서, 최소 연박 수를 생략하면 1박으로 동작하기를 원한다.
8. 캠핑 이용자로서, 감시 조건을 여러 개 등록하고 각각 이름을 붙이고 싶다. 알림에서 어떤 조건에 걸렸는지 구분하기 위해서다.
9. 캠핑 이용자로서, 없는 구역 코드나 자리 번호를 적으면 폴러가 시작하지 않고 어느 줄이 틀렸는지, 고를 수 있는 값이 무엇인지 알려 주기를 원한다. 오타 때문에 조용히 감시가 안 되는 일을 막기 위해서다.
10. 캠핑 이용자로서, 예약처의 최대 박수(고래불은 2박)를 넘는 연박 수를 적으면 설정 오류로 알려 주기를 원한다.
11. 캠핑 이용자로서, 선택할 수 있는 구역과 자리 번호를 CLI 명령(`catalog`)으로 표처럼 보고 싶다. 설정을 쓸 때 참고하기 위해서다.
12. 운영자로서, `catalog --live`로 사이트를 한 번 조회해서 어댑터에 고정된 구역·자리 목록과 실제 사이트가 다른지 점검하고 싶다. 사이트가 개편된 것을 미리 알기 위해서다.
13. 운영자로서, Telegram 토큰 같은 비밀값은 환경 변수로 넣고 설정 파일에서는 `${VAR}`로 참조하고 싶다. 설정 파일을 git에 올려도 안전하게 하기 위해서다.
14. 운영자로서, 참조한 환경 변수가 비어 있으면 폴러가 시작을 거부하기를 원한다.
15. 운영자로서, 설정을 바꾼 뒤 재시작하면 반영되기를 원한다(핫 리로드는 없다).

### 빈자리 감지와 알림

16. 캠핑 이용자로서, 감시 조건에 맞는 자리가 비면 Telegram 알림을 받고 싶다. 바로 예약하러 가기 위해서다.
17. 캠핑 이용자로서, 알림에 시설, 구역 이름, 자리 번호, 입실일(요일), 박수, 감시 조건 이름이 보이기를 원한다.
18. 캠핑 이용자로서, 알림에 (구역, 입실일)별 예약 화면으로 가는 버튼이 있기를 원한다. 한 번 눌러 예약 화면에 들어가기 위해서다.
19. 캠핑 이용자로서, 같은 빈자리에 대해 매 바퀴마다 알림이 반복되지 않기를 원한다. **새로 생긴** 빈자리만 알림받는다.
20. 캠핑 이용자로서, 이미 알림받은 빈자리가 사라졌다가 다시 생기면 다시 알림받고 싶다.
21. 캠핑 이용자로서, 한 바퀴에서 빈자리가 여러 개 나와도 알림 대상 하나당 메시지 한 건으로 묶여 오기를 원한다. 메시지 안에서는 감시 조건별로 나뉜다.
22. 캠핑 이용자로서, 메시지가 너무 길면 나뉘어 오되 내용은 빠지지 않기를 원한다.
23. 캠핑 이용자로서, 빈자리가 많아 버튼이 8개를 넘으면 나머지는 본문 링크로 받고 싶다.
24. 캠핑 이용자로서, 폴러가 재시작한 뒤 첫 알림에는 "재시작 직후 현황" 표시가 있기를 원한다. 새로 생긴 빈자리인지 원래 있던 것인지 구분하기 위해서다.
25. 캠핑 이용자로서, 지인과 함께 쓰는 그룹 채팅과 내 1:1 채팅을 알림 대상으로 따로 등록하고, 감시 조건마다 어느 대상으로 보낼지 고르고 싶다.
26. 캠핑 이용자로서, 감시 조건에 알림 대상을 지정하지 않으면 `default` 대상으로 보내기를 원한다.
27. 운영자로서, 봇 하나에 알림 대상마다 `chatId`만 다르게 쓰고 싶다.
28. 운영자로서, `telegram chats` CLI로 봇이 최근 받은 업데이트에서 chat 목록을 보고 싶다. chatId를 쉽게 찾기 위해서다.
29. 캠핑 이용자로서, Telegram 전송이 실패한 빈자리는 다음 바퀴에 다시 알림받고 싶다. 알림을 놓치지 않기 위해서다.
30. 캠핑 이용자로서, 입실일 범위가 모두 지나간 감시 조건은 "만료" 알림을 한 번 받고 싶다. 설정을 정리할 때를 알기 위해서다.
31. 캠핑 이용자로서, 아직 예약이 열리지 않은 날짜(D−30일 10시 이전)는 오류 없이 대기하다가 열리면 자동으로 감시되기를 원한다.
32. 캠핑 이용자로서, 당일 입실은 예약 마감(고래불 18시)이 지나면 감시에서 빠지기를 원한다.

### 폴링 매너와 스케줄

33. 운영자로서, 폴러가 예약처마다 요청을 하나씩 순서대로 보내고, 요청 사이에 최소 간격(기본 5초에 0~3초 지터)을 지키기를 원한다. 사이트에 부담을 주지 않기 위해서다.
34. 운영자로서, 한 바퀴가 끝난 뒤 설정한 간격(기본 150초, ±20% 지터)만큼 쉬기를 원한다. 감시 조건이 늘어도 요청 빈도가 과해지지 않게 하기 위해서다.
35. 운영자로서, 간격을 60초 미만으로 설정하면 거부되기를 원한다. 실수로 사이트를 과하게 두드리는 일을 막기 위해서다.
36. 운영자로서, 같은 조회 단위를 공유하는 감시 조건들이 한 번만 조회되기를 원한다.
37. 운영자로서, 고래불은 월 캘린더의 잔여 수로 먼저 걸러서 잔여가 있는 (구역, 날짜)만 자세히 조회하기를 원한다. 평소 한 바퀴를 요청 1~2회로 끝내기 위해서다.
38. 운영자로서, 모든 요청에 도구 이름을 밝힌 정직한 User-Agent가 붙고, 설정으로 문구만 덧붙일 수 있기를 원한다. 브라우저 위장이나 개인정보는 넣지 않는다.
39. 운영자로서, 선택적으로 quietHours(예: 02:00~06:00)를 두고 싶다. 이 시간에는 간격이 3배로 늘고 알림이 무음으로 오게 하기 위해서다.
40. 운영자로서, 예약처가 여러 개일 때 첫 바퀴 시작 시각이 분산되기를 원한다.
41. 운영자로서, robots.txt가 막은 경로(고래불 `/bbs/`)는 절대 호출되지 않기를 원한다.

### 헬스와 운영

42. 운영자로서, 차단 페이지를 받으면 그 예약처의 폴링이 즉시 멈추고, 원인과 조치 방법이 담긴 알림을 받고 싶다. 차단된 사이트에 계속 요청을 보내지 않기 위해서다.
43. 운영자로서, 사이트 구조가 바뀌어 파싱할 수 없는 상태가 연속 2바퀴 이어지면 폴링이 멈추고 알림받고 싶다. "빈자리 0개"로 착각하지 않기 위해서다.
44. 운영자로서, 네트워크 오류나 5xx가 나면 간격을 두 배씩 늘려(상한 30분) 재시도하고, 성공하면 원래 간격으로 돌아오기를 원한다.
45. 운영자로서, 일시 오류가 5바퀴 이상, 15분 이상 계속되면 `degraded` 알림을 한 번 받고, 회복되면 `recovered` 알림을 받고 싶다.
46. 운영자로서, 사이트가 점검 중이면 30분 간격으로 확인을 계속하되 알림은 한 번만 받고 싶다.
47. 운영자로서, 같은 장애 상태가 이어지면 24시간마다 한 번만 리마인드를 받고 싶다.
48. 운영자로서, 한 예약처가 멈춰도 다른 예약처는 계속 돌기를 원한다.
49. 운영자로서, 멈춘 예약처는 프로세스를 재시작해야 재개되기를 원한다. 자동 재시도는 없다.
50. 운영자로서, 매일 정해진 시각(기본 09:00)에 무음 일일 요약을 받고 싶다. 예약처별 상태, 전날 바퀴 수와 실패 수, 활성 감시 조건 수, 곧 만료될 감시 조건이 들어간다. 조용한 날에도 폴러가 살아 있는지 알기 위해서다.
51. 운영자로서, 선택적으로 dead-man ping URL을 설정하고 싶다. 바퀴가 끝나고 알림 채널이 정상일 때만 ping이 가게 해서, 프로세스나 알림 채널이 죽은 것을 외부 서비스가 알려 주게 하기 위해서다.
52. 운영자로서, `/healthz`(기본 localhost 바인드)로 메인 루프가 살아 있는지 확인하고 싶다.
53. 운영자로서, 메인 루프가 멈추면 watchdog이 프로세스를 종료하고 Docker restart 정책이 다시 띄우기를 원한다. 의도적으로 멈춘 예약처는 재시작 대상이 아니다.
54. 운영자로서, `docker compose up` 한 번으로 설정 파일 마운트, env 파일, 재시작 정책, 헬스체크가 모두 갖춰진 채로 폴러를 띄우고 싶다.
55. 운영자로서, amd64와 arm64에서 모두 이미지를 빌드할 수 있기를 원한다. 나중에 라즈베리파이나 NAS로 옮기기 위해서다.
56. 운영자로서, 로그가 JSON 줄 단위로 stdout에 남고 로테이션되기를 원한다. 비밀값은 로그에 남지 않는다.
57. 운영자로서, 모든 시간 계산이 호스트 설정과 무관하게 KST 기준이기를 원한다.

### 확장성

58. 개발자로서, 새 예약처를 추가할 때 어댑터 하나만 구현하면 되기를 원한다. 코어의 매칭, 스케줄, 알림, 헬스 로직을 재사용하기 위해서다.
59. 개발자로서, 브라우저가 필요한 예약처가 생기면 그 어댑터만 Playwright를 쓰고, 브라우저가 필요 없는 이미지에는 Playwright가 들어가지 않기를 원한다.
60. 개발자로서, 어댑터가 전역 `fetch`를 쓰면 lint에 걸리기를 원한다. 매너 규칙(UA, 간격, 차단 감지)을 빠뜨리지 않기 위해서다.
61. 개발자로서, 새 알림 채널을 추가할 때 Notifier 플러그인 하나만 구현하면 되기를 원한다.

## Implementation Decisions

### 스택

- TypeScript/Node LTS 단일 패키지로 만든다. HTTP는 Node 내장 `fetch`, HTML 파싱은 `cheerio`, 설정 검증은 `zod`, 로그는 `pino`를 쓴다.
- 스케줄 루프는 직접 구현한다. 크롤링 프레임워크(Crawlee, Scrapy 등)는 쓰지 않는다. 링크를 따라가는 크롤러용이라 이 용도와 구조가 맞지 않고, 위장·세션 로테이션·robots 무시 같은 기본값이 매너 원칙과 충돌한다.
- `croner`와 `tough-cookie`는 필요해지면 추가한다. 고래불에는 쿠키가 필요 없다.
- Playwright는 `optionalDependencies`에 두고 브라우저 어댑터에서만 dynamic import한다. 1차 구현에서는 쓰지 않는다.

### 모듈

- **설정 로더**: YAML을 읽고 `${VAR}`를 치환한다. 그다음 zod로 구조를 검증하고, 로드된 어댑터의 `describe()`와 대조해 의미를 검증한다. 오류가 있으면 위치와 고를 수 있는 값을 담아 시작을 거부한다.
- **스케줄러 / 바퀴 실행기**: 예약처별 루프다.
  - 활성 감시 조건을 조회 단위로 전개한다. 이때 예약 창 밖의 날짜, 이미 지난 날짜, 당일 마감이 지난 날짜, 요일 필터에 걸리는 날짜를 뺀다.
  - 같은 조회 단위는 하나로 합친다.
  - 어댑터를 호출하고, 결과를 감시 조건의 자리 필터와 매칭해 빈자리를 만든다.
  - 바퀴가 끝나면 지터를 섞은 간격만큼 쉰다. 백오프와 quietHours 배율도 여기서 적용한다.
- **빈자리 추적기(메모리)**: 알림 대상별로 "알렸음" 집합을 둔다. 키는 (감시 조건, 자리, 입실일, 박수)다.
  - 이번 바퀴에 새로 나타난 빈자리만 알림 후보로 삼는다.
  - 전송에 성공한 뒤에만 집합에 넣는다.
  - 빈자리가 사라지면 집합에서 뺀다. 다시 나타나면 다시 알린다.
  - 영속 저장소는 없다. 재시작 뒤 첫 바퀴는 `startupSnapshot`으로 표시한다.
- **공통 HTTP 클라이언트 (`ctx.http`)**
  - 정직한 UA `overlord-availability-poller/<version>`를 고정으로 붙이고, 설정의 suffix만 덧붙일 수 있다. `From` 헤더는 넣지 않는다.
  - 예약처별로 요청을 직렬화하고 최소 간격과 지터를 지킨다.
  - 타임아웃은 10초다.
  - 모든 응답에 예약처가 등록한 차단 판별 함수를 적용한다. 차단 페이지는 HTTP 200으로 오기 때문에 본문으로 판별한다.
  - 쿠키 저장소는 선택 기능이다.
  - 실제 네트워크 호출은 주입 가능한 **Transport**에 위임한다. 이 경계가 테스트 seam이다.
- **예약처 어댑터 인터페이스**

  ```ts
  interface ProviderAdapter {
    readonly id: string;
    describe(): ProviderInfo;   // 시설·구역(코드, 이름, 유형, 정원, 자리 번호 목록), maxNights,
                                // openingRule(입실일 D가 열리는 시각, 당일 마감 시각), deepLink(시설, 구역, 입실일)
    init?(ctx: AdapterContext): Promise<void>;
    queryAvailability(q: { facility; zone; checkIn; nights }, ctx): Promise<AvailableSite[]>; // N박 연속 빈 자리만
    queryAvailabilityBatch?(units, ctx): Promise<Map<Unit, AvailableSite[]>>;
    dispose?(): Promise<void>;
  }
  // 실패: AdapterError{ kind: 'transient' | 'blocked' | 'unrecognized' | 'unavailable' }
  ```

  - "빈자리 0개"는 정상 결과다. 다만 파싱이 성공했다는 근거(구조 검증)를 확인한 뒤에만 0개로 인정한다.
  - 구역과 자리 목록은 어댑터 코드에 고정값으로 둔다.
- **고래불 어댑터**
  - `queryAvailabilityBatch`: 필요한 월의 캘린더(`/pages/sub.htm?nav_code=gor1501675800&view_cate=YYYY&view_cate2=MM`)를 조회한다. 1박 잔여가 1 이상인 (구역, 날짜)만 `/pages/zoneAreaAjax.htm?res_Day=…&room_Code=…&site_date=<박수>`로 자세히 조회한다.
    - 빈 자리는 class가 `num`뿐이고 `zone_area_select(...)` onclick이 있는 자리다. `num ban`, `num ing`, `num wait`는 빈 자리가 아니다.
  - 구조 검증: 캘린더 날짜 셀 수, `div.select_room` 컨테이너의 존재, 자리 수가 고정값과 크게 다르지 않은지를 본다.
  - 차단 판별: "영덕군 전산팀" 안내가 담긴 약 915바이트짜리 차단 페이지를 가려낸다.
  - 오픈 규칙: 입실일 D는 D−30일 10:00에 열린다. 당일 입실 마감은 18:00이다. 최대 2박이다.
  - 딥링크는 step01 URL(`…&mode=step01&type=<구역>&today=<입실일>`)이다. NetFunnel을 거치지 않는다.
  - `/bbs/` 경로는 호출하지 않는다. 폼도 전송하지 않는다.
  - 구역 코드: CAA, CAB(카라반 4·6인), DKA, DKB, DKC(숲속야영장 A·B·C), AUA(캠핑카존), PEA, PEB, PEC(펜션형). 펜션형 인원 대응과 폐쇄된 카라반 번호는 구현하면서 fixture로 확정한다.
  - 설정의 자리 표기(`A02`)를 사이트 식별자(내부 idx, `dka_2`, "텐트사이트 A02호")와 어떻게 대응시킬지는 어댑터가 정한다.
- **헬스 모니터**
  - 예약처별 상태 머신: `ok` → `degraded` / `unavailable` / `stopped(blocked|unrecognized)`.
  - 상태가 바뀔 때만 health 이벤트를 낸다. 같은 상태가 이어지면 24시간마다 리마인드한다.
  - `degraded`는 transient가 연속 5바퀴 이상이고 15분 이상 이어진 경우다.
  - `unrecognized`는 구조 검증이 연속 2바퀴 실패한 경우다. `blocked`는 한 번이면 즉시 정지한다.
  - `stopped`는 재시작해야 풀린다.
  - 일일 요약 이벤트를 만든다. 선택적으로 dead-man ping을 보내는데, 바퀴가 끝나고 알림 채널이 정상일 때만 보낸다.
  - `/healthz`는 메인 루프가 살아 있는지만 본다. 틱이 오래 멈추면 watchdog이 프로세스를 종료한다.
- **알림 플러그인**

  ```ts
  type NotificationEvent =
    | { kind: 'openings'; cycleId; startupSnapshot: boolean; groups: { watch; openings: Opening[] }[] }
    | { kind: 'health'; provider; status: 'blocked'|'unrecognized'|'unavailable'|'recovered'|'degraded'; detail }
    | { kind: 'watchExpired'; watch }
    | { kind: 'heartbeat'; summary };
  interface Notifier { readonly type: string; send(event, opts: { silent: boolean }): Promise<void>; }
  ```

  - 렌더링은 플러그인이 한다. 코어는 공통 문구 헬퍼를 제공한다.
  - quietHours에는 모든 이벤트를 `silent`로 보낸다.
- **Telegram Notifier**
  - `parse_mode: HTML`로 보낸다.
  - 헤더는 🏕 빈자리 발견 또는 🔄 재시작 직후 현황이다. 감시 조건별 블록에 `날짜(요일) N박 · 구역명 · 자리 번호들`을 적는다.
  - (구역, 입실일)별 인라인 URL 버튼을 최대 8개까지 붙인다. 넘치는 것은 본문 링크로 넣는다.
  - 4096자를 넘으면 나눠 보낸다.
  - `silent`면 `disable_notification`을 켠다.
  - 재시도: `429`는 `retry_after`를 지키고, 5xx와 네트워크 오류는 최대 3회까지 재시도한다. 그래도 실패하면 로그만 남긴다.
  - 봇은 전송만 한다. 명령어를 받지 않는다.
- **CLI**: 폴러 실행(기본), `catalog <provider> [--live]`, `telegram chats`.

### 설정 스키마 (결정을 담은 예시)

```yaml
userAgentSuffix: ""
quietHours: { from: "02:00", to: "06:00" }       # 선택, 기본 없음
dailySummary: { enabled: true, at: "09:00" }
deadManPingUrl: ${DEADMAN_URL}                    # 선택
healthz: { bind: "127.0.0.1:8080" }
providers:
  goraebul: { pollIntervalSeconds: 150, minRequestGapSeconds: 5 }   # 간격 하한 60
notifiers:
  default: { type: telegram, botToken: ${TELEGRAM_BOT_TOKEN}, chatId: ${TELEGRAM_CHAT_ID} }
watches:
  - name: 10월 주말 숲속야영장
    provider: goraebul
    facility: goraebul          # 예약처에 시설이 하나뿐이면 생략 가능
    zones: [DKA, DKB]
    sites: [A01, A02, "A10-A15"] # 생략하면 구역 안의 모든 자리
    checkIn: { from: 2026-10-01, to: 2026-10-31 }   # 입실일 기준
    weekdays: [fri, sat]
    nights: 1                   # 최소 N박, 예약처 maxNights 이하
    notify: [default]
```

### 운영

- Node LTS slim 기반 multi-stage 이미지로 빌드한다. 브라우저는 넣지 않고, `WITH_BROWSER` 빌드 인자는 이후를 위해 자리만 둔다. amd64와 arm64를 지원한다. 레지스트리 없이 운영 기기에서 빌드한다.
- `docker compose`로 설정 파일 마운트, `env_file`, `restart: unless-stopped`, `/healthz` 기반 `HEALTHCHECK`, json-file 로그 로테이션(10m×3)을 구성한다. `TZ=Asia/Seoul`로 고정한다.
- 1차 운영 장소는 사용자의 WSL/개인 PC Docker다. 국내 가정용 IP에서 돈다.

## Testing Decisions

- **좋은 테스트의 기준**: 사용자가 관찰할 수 있는 결과만 검증한다. 무엇이 Telegram으로 나갔는지, 사이트에 어떤 요청이 언제 몇 번 나갔는지, 폴러가 시작을 거부했는지를 본다. 내부 자료구조, 호출 순서, 비공개 함수는 검증하지 않는다.
- **주 seam (하나)**: 폴러 전체(코어 + 고래불 어댑터 + Telegram Notifier)를 실제 설정 YAML로 띄우고, 바깥 경계 세 곳만 바꿔 끼운다.
  1. **Transport**: HTTP 요청을 받아 응답을 돌려주는 함수다. 시나리오별로 응답을 스크립트한다.
  2. **Clock**: 현재 시각과 sleep이다. 가짜 시계를 앞으로 돌려 바퀴, 백오프, 예약 오픈 시각, 당일 마감, quietHours, 일일 요약, 24시간 리마인드를 재현한다.
  3. **Telegram Sink**: Telegram Bot API 호출(sendMessage 등)을 기록하고 성공이나 실패를 흉내 낸다.
- **이 seam으로 검증할 시나리오**
  - 새 빈자리 알림과 재알림 방지
  - 사라졌다 다시 생긴 빈자리의 재알림
  - 재시작 직후 현황 표시
  - 감시 조건별 묶음 전송, 알림 대상별 분리 전송
  - 캘린더 선필터 효과: 매진이면 캘린더 요청만 나간다
  - 조회 단위 합치기, 요청 간격과 순차 전송, UA 헤더
  - `/bbs/` 경로를 호출하지 않는지
  - 예약 창 밖 날짜와 당일 마감 제외, 감시 조건 만료
  - 차단 페이지를 받으면 즉시 정지하고 다른 예약처는 계속 도는지
  - 구조 변경이 2바퀴 이어지면 정지하는지
  - transient 백오프와 degraded, recovered 전이, unavailable 처리, 24시간 리마인드
  - quietHours의 무음 전송과 간격 배율
  - Telegram 전송 실패 뒤 다음 바퀴 재전송, 429 retry_after 준수
  - 메시지 분할, 버튼 8개 초과 처리
  - dead-man ping 조건
- **Fixture**: 조사 단계에서 저장한 실제 고래불 HTML(`research/raw/`, `research/raw/2026-09-29/`)을 응답 fixture로 쓴다. 월 캘린더, `zoneAreaAjax` 1박·2박, step01, 차단 페이지가 들어 있다. 구조가 깨진 응답과 5xx는 이 fixture를 변형하거나 합성해서 만든다. fixture는 테스트 소스 트리로 복사해 고정한다. 첫 정찰 fixture는 수집할 때 쓴 UA가 무엇인지 모른다(`goraebul-recon.md` 참고).
- **보조 진입점**: 설정 검증과 `catalog`는 "설정을 로드한 결과와 오류 메시지" 또는 "CLI 출력"으로 확인한다. `catalog --live`와 `telegram chats`도 같은 Transport와 Sink 교체로 검증한다.
- **내부 모듈 단위 테스트는 두지 않는다.** 파서, 상태 머신, 매칭 로직은 모두 주 seam을 통해 검증한다.
- **기존 사례**: 없다. 새 저장소다. 이 spec의 seam이 이후 어댑터 테스트의 기준이 된다. 새 어댑터도 자기 fixture로 같은 seam 테스트를 추가한다.
- 실제 사이트를 호출하는 테스트는 CI에 두지 않는다.

## Out of Scope

- 자동 예약(예약 매크로), 폼 전송, NetFunnel 대기열 진입.
- 대기열, captcha, 봇 탐지, UA 차단 우회. 브라우저 위장, UA 로테이션, 프록시 로테이션도 포함한다.
- 숲나들e(칠곡송정자연휴양림) 어댑터. 이후 별도 지도에서 다룬다. 확장 지점(`init`/`dispose`, 선택 의존성)만 마련해 둔다.
- 예약 오픈 시각(매일 10시) 경쟁 대응. 이 시각 전후로 간격을 조이지 않는다.
- Telegram 봇 명령어로 감시 조건 관리, `/status` 명령.
- 영속 저장소, 설정 핫 리로드.
- 다중 사용자 서비스, 계정, 웹 UI.
- 빈자리가 사라졌을 때의 알림(메시지 수정이나 마감 알림).
- Telegram 외 알림 채널 구현. 플러그인 인터페이스만 둔다.
- 이미지 레지스트리 배포, VPS나 홈서버 이전.

## Further Notes

- **매너·법적 전제**: 고래불은 브라우저가 아닌 기본 UA를 차단 페이지로 막는다. 도구 이름을 밝힌 정직한 UA로는 정상 응답이 왔다. 사용자는 영덕군 전산팀에 문의하지 않기로 했다(2026-09-29). 그러므로 정직한 UA, 차단을 감지하면 정지, robots.txt 준수는 협상할 수 없는 요구사항이다. 근거는 [research/polling-etiquette.md](research/polling-etiquette.md)에 있다. 법률 자문이 아니다.
- **폴링 간격**: 운영 기본값 150초는 사용자 결정이다. 조사 권장값은 60초였고, 국내 사례는 5분이다.
- **미검증 항목**: 구현할 때 fixture로 확인한다.
  - 선점(`num ing`)과 취소대기(`num wait`) 상태의 실제 마크업
  - 10:00에 날짜가 열리는 전환 동작
  - 펜션형 구역 코드와 인원 대응
  - 데이터센터나 해외 IP 차단 여부
- **개인정보**: 조사 중 한 차례 요청의 UA 헤더에 사용자 이메일이 실려 나간 적이 있다. 구현에서는 어떤 헤더에도 개인정보가 들어가지 않아야 한다.
- 결정별 세부 근거는 [map.md](map.md)의 Decisions so far에서 각 티켓으로 이동해 확인한다.
